# RAG框架缺陷标注手册

更新日期：2026-11-14。

本手册对应《RAG框架缺陷特征与修复策略的实证研究》的最终分类体系及本仓库的数据字段。研究对象为RAGFlow、AnythingLLM、FastGPT和Kotaemon，基本分析单元为一条Issue及其选定的关联PR。`BUG汇总.xlsx`为一级标注主表；`data/RAG根因二级标注.csv`通过`issue_html_url`与主表关联。

## 1. 研究范围与标注对象

本研究关注RAG框架自身的软件缺陷，包括框架实现及其维护的配置、依赖声明和部署设置中不符合预期功能或处理约定的问题。纯文档修改、使用咨询、功能请求，以及没有直接修复关系的Issue–PR关联，不作为框架自身缺陷的判定依据。

对于用户使用方式、外部数据、模型输出或运行环境引起的异常，应先核对框架声明的支持范围和处理约定。框架行为符合约定、异常仅由不当使用、知识内容缺失或模型输出波动引起时，按筛选规则排除；若外部因素触发了框架本应处理而未正确处理的问题，则结合相关实现和针对性修改判断框架自身的缺陷。

每条样本在以下维度各保留一个主标签：

- **功能阶段**：缺陷涉及的主要功能阶段。
- **运行症状**：用户或调用方能够直接观察到的异常表现。
- **一级根因**：造成异常的主要实现或配置问题。
- **修复策略**：处理主要根因所采用的核心修改方式。

一级根因标注完成后，再为每条样本判定“RAG特有根因”或“通用根因”。二级判定不替换一级标签。

## 2. 证据与根因判定

### 2.1 缺陷、错误状态与失效

参照Fault–Error–Failure模型，框架实现或配置中的缺陷在特定条件下被触发后，可能使参数取值、数据内容、对象关系或资源状态偏离预期，形成内部错误状态；这种偏差影响对外提供的功能时，表现为可观察的失效。症状标注描述外部表现，根因标注归纳导致异常的主要实现或配置问题。

理论参照：Avizienis等，*Basic Concepts and Taxonomy of Dependable and Secure Computing*，2004，DOI：[10.1109/TDSC.2004.2](https://doi.org/10.1109/TDSC.2004.2)。

### 2.2 证据使用步骤

1. 阅读Issue的正文、复现步骤、日志、调用栈、截图和评论，记录触发条件、预期行为及实际表现。
2. 核对选定PR与该异常的修复关系，阅读修改说明、修复前后实现、相关上下文、测试变更和开发者讨论。
3. 分析实现或配置问题如何改变参数、数据、状态或资源，以及这种变化能否解释Issue报告的症状。
4. 检查核心补丁是否针对该问题，并区分用户使用、外部数据、模型输出和环境因素的影响。
5. 有对应测试结果或修复后反馈时，核对触发条件与预期行为是否一致，将其作为补充证据。

内部错误状态可能来自运行记录，也可能由实现逻辑推断。复核记录应注明证据来源。PR合并和Issue关闭用于确认处理状态，不能单独证明目标症状已经消失。本研究未对全部样本开展历史版本复现与回归测试；修复效果的核对依据公开评论、PR记录及其中已有的测试或反馈。

### 2.3 Issue与PR的对应

- 先判断修复关系，再检查合并状态。PR中出现Issue编号、相互引用或关闭关键词，均需结合实际修改核实。
- 同一Issue涉及多个PR时，核实各自作用，只保留选定的一条关联PR。多个PR均已合并且能够修复目标问题时，按采集规则保留最新合并的一条，并记录选择依据。
- 版本发布、功能集合、重构或多问题混合PR的总变更规模，不直接代表目标Issue的修复规模。RQ3另按已记录的16条排除名单筛选，不能将这一排除名单理解为从333条一级标注数据中删除样本。
- diff较长时，先定位修改文件、相关函数和测试，再检查与Issue直接相关的修改片段。仅凭文件名或PR标题不足以确定根因。

## 3. 主表字段与写作要求

主表保留原有23个字段，程序标签采用下文列出的英文值。中文名称用于论文及阅读说明。

| 字段 | 含义与要求 |
| --- | --- |
| `bug_issue_title` | 原Issue标题；不作为根因判定的唯一依据。 |
| `issue_html_url` | Issue链接，也是跨文件关联的唯一标识。 |
| `bug_stage` | 唯一主功能阶段。 |
| `bug_issue_summary` | 用中文概括完整问题，交代触发场景、异常行为及受影响功能。 |
| `bug_run_symptom_summary` | 用中文说明用户或调用方实际看到的影响，不重复问题总结或直接翻译标题。 |
| `bug_run_symptom_type` | 唯一主症状。 |
| `bug_root_cause_summary` | 用中文说明主要实现或配置问题，以及它如何造成异常。 |
| `bug_root_cause_type` | 唯一主根因。 |
| `how_to_fix_bug` | 用中文直接说明修改了什么、如何恢复预期行为。 |
| `fix_strategy` | 主修复策略；与第7节的主表标签对应。 |
| `pr_title`、`pr_url` | 选定PR的标题与链接。 |
| `pr_diff_url` | 选定PR的diff地址。 |
| `pr_modified_files` | 修改文件列表，多个路径以分号分隔。 |
| `pr_changed_files` | 选定PR修改的文件数量。 |
| `pr_changed_code_line` | 保存的PR新增与删除行数之和，部分值同时记录增删明细。 |
| `issue_created_at`、`issue_closed_at` | Issue创建与关闭时间，按原始UTC时间保存。 |
| `created_to_closed_days` | 采集表保留的整数天数；连续时间统计应由上述时间戳重新计算。 |
| `issue_comments` | Issue评论数量，不包含PR评论。 |
| `issue_number`、`issue_id` | Issue编号与GitHub标识；编号仅在所属仓库内唯一。 |
| `issue_state` | 保存时的Issue状态。 |

四个总结字段应描述缺陷本身。根据问题复杂程度写一至三句话，避免“本字段说明”“相关执行路径存在问题”“PR修改某文件”等不能解释具体问题的模板句。修复说明不要求逐个复述文件名。

## 4. 功能阶段

阶段标注以Issue、相关实现和核心修复共同指向的主要功能为依据，而不是用户最后看到异常的界面，也不要求通过动态跟踪确定“最早产生错误状态”的位置。

| 标签 | 中文名称 | 定义与边界 |
| --- | --- | --- |
| `knowledge_preparation` | RAG框架知识准备 | 将外部内容转换为可索引知识的过程，包括内容导入、读取、解析、OCR、清洗、分块、嵌入生成及初始索引构建和写入。 |
| `retrieval_reranking` | 检索与重排 | 为当前查询选择已有知识，包括查询扩展、召回、过滤、Top-K、混合检索、候选组织和重排。 |
| `response_generation` | 响应生成 | 组织模型输入并形成响应，包括提示词、历史消息、证据上下文、生成过程、流式返回、答案后处理和引用组织。 |
| `knowledge_base_management` | 知识库管理 | 管理知识库、文档、分块及相关资源的归属、关联、可见性、更新、删除和同步状态。 |
| `model_provider_integration` | 模型与服务接入 | 接入模型、嵌入器、重排器、向量数据库、OCR或其他外部服务时的SDK、认证、请求与响应适配。 |
| `workflow_agent_orchestration` | 工作流与智能体编排 | 多节点、工具或Agent之间的调度、分支、循环、调用顺序及跨步骤状态和数据传递。 |
| `ui_api_deployment` | 系统交互与运行支撑 | 通用页面、表单、路由、API入口、身份访问、容器、启动脚本、环境设置及运行支撑。 |

主要边界如下：

- 初次将内容解析、切分并建立索引，归知识准备；已有文档与索引在更新、删除后不同步，归知识库管理。
- 候选证据如何召回、过滤或排序，归检索与重排；证据如何进入提示词或最终响应，归响应生成。
- 外部服务的请求和响应契约适配，归模型与服务接入；服务调用前的语义输入组织，归响应生成。
- 多节点之间的执行关系出错，归工作流与智能体编排；单个节点内部的解析、检索等问题，归该节点承担的主要功能。
- UI或API仅呈现异常，而核心修复位于上述其他环节时，按核心问题所在功能判定。

## 5. 运行症状

| 标签 | 中文名称 | 定义 | 示例 |
| --- | --- | --- | --- |
| `functional_failure` | 功能失效 | 主要异常是结果、状态或行为不符合预期，未以明确异常终止作为主要表现。 | 文档被标记为已嵌入但无法检索；分块配置不生效；引用或界面状态错误。 |
| `crash` | 运行崩溃 | 系统进入正常服务后，当前任务、请求或进程因异常而中断。 | 文档解析抛出未处理异常；模型请求返回500并终止；任务执行失败。 |
| `build_failure` | 构建与启动失败 | 安装、构建、部署、启动或初始化阶段失败，系统尚未进入正常服务状态。 | 依赖安装失败；镜像构建失败；启动脚本报错。 |
| `performance_cost_issue` | 性能与成本异常 | 主要异常是延迟、挂起、阻塞、超时，或资源、Token与调用成本异常增加。 | 请求长期无响应后超时；模型重复下载；重复生成造成额外开销。 |

症状以Issue主要报告且核心修复针对的外部影响为准。启动前失败与运行中中断应分开；以挂起或效率异常为主要表现、最终由超时机制结束的请求，可归性能与成本异常。重复输出导致内容错误时按功能失效判断，只有证据指向重复计算、延迟或成本等主要影响时才归性能与成本异常。不能仅根据“超时”“重复”等关键词选标签。

解析、索引、检索和生成不是症状类别；它们的位置由功能阶段表示。数据丢失、错误引用、配置不生效等若主要表现为错误结果或状态，归功能失效。安全问题的外部症状与安全根因分别判断。

## 6. 根因

### 6.1 八类一级根因

| 标签 | 中文名称 | 定义与判定重点 |
| --- | --- | --- |
| `data_processing_error` | 数据处理错误 | 内容在解析、抽取、编码、类型或格式转换、序列化、分块及读写过程中被错误处理。包括Chunking分块策略实现错误，重点是转换或处理后的数据不符合预期。 |
| `logic_validation_error` | 逻辑与校验错误 | 条件分支、缺失值与默认值、边界条件、参数校验或策略控制不正确。包括检索、召回、过滤、Top-K、Rerank及混合检索参数未按预期生效。 |
| `api_contract_error` | 接口契约错误 | 调用方与被调用方在字段名称、参数类型或顺序、输入输出结构、协议及兼容约定上不一致，涉及内部接口和外部服务接口。 |
| `state_consistency_error` | 状态一致性错误 | 状态在组件、请求、会话、时间点或存储副本之间未正确更新、隔离或保持对应，或者实际失败被报告为成功。 |
| `dependency_environment_error` | 依赖与环境错误 | 框架维护的依赖声明、版本约束、配置、路径、镜像、环境变量或部署设置与运行要求不兼容。应确认问题属于框架维护责任，而非单纯的用户错误配置。 |
| `resource_mismanagement` | 资源管理不当 | 资源分配、复用、释放、生命周期、处理容量或并发控制不当，包括连接、线程、队列、文件、监视器、重复初始化和资源阻塞问题。 |
| `security_vulnerability` | 安全漏洞 | 身份认证、授权、对象所有权、租户隔离或敏感操作保护缺失或错误，造成未经授权的访问、操作或信息暴露。 |
| `prompt_context_error` | 提示词与上下文错误 | 模型实际接收的语义输入在选择、组织、格式化或裁剪中出错，包括提示模板、角色消息、历史窗口、证据装配、工具结果、多模态输入及Token预算处理。 |

根因选择以核心补丁直接处理的主要问题为准。不要按类别名称、文件所在目录或固定优先级机械选取标签，也不将逻辑与校验错误作为证据不足时的默认类别。

### 6.2 易混类别的边界

- **数据处理与逻辑校验**：数据转换、解析或分块实现本身错误，归数据处理；外围分支、默认值或边界判断使正确处理步骤未按要求执行，归逻辑校验。
- **数据处理与接口契约**：单个组件内部的数据处理错误，归数据处理；交互双方对同一字段、类型或结构的约定不一致，归接口契约。
- **接口契约与依赖环境**：框架构造的请求或解释的响应不符合接口约定，归接口契约；依赖版本、安装声明或部署设置导致无法满足运行条件，归依赖环境。
- **状态一致性与数据处理**：同一操作中的表示转换错误，归数据处理；更新、删除、并发或跨会话操作后各处状态不一致，归状态一致性。
- **状态一致性与资源管理**：核心修复维护业务对象状态的同步或隔离，归状态一致性；核心修复处理资源生命周期、调度、互斥或容量，归资源管理。
- **提示词上下文与逻辑校验**：直接修正模型输入的内容、角色组织、证据装配或窗口裁剪，归提示词上下文；修正召回、过滤、重排策略本身，归逻辑校验，即使其最终影响回答。
- **提示词上下文与接口契约**：模型输入的语义内容或消息选择出错，归提示词上下文；消息结构不满足服务接口的格式约定，归接口契约。
- **安全与一般校验**：核心问题是身份、权限、对象所有权或租户边界被破坏，归安全；普通参数范围或缺失值处理，归逻辑校验。

### 6.3 RAG特有根因与通用根因

在一级标签内部进一步判定缺陷是否直接破坏文档分块、知识索引、嵌入表示、检索策略或证据上下文组织等RAG处理规则。需要结合这些规则解释直接错误行为时，标记为RAG特有根因；其他样本标记为通用根因。

两类样本在底层错误形式上可以具有共性。例如条件判断、接口调用或状态更新错误，既可能影响一般系统功能，也可能破坏RAG处理规则。二级标签对每个样本进行互斥划分，不能把某个一级类别整体判为RAG特有。

| 一级根因 | RAG特有情形的判定依据 | 类别样本数 | RAG特有数 | 类内比例 |
| --- | --- | ---: | ---: | ---: |
| 数据处理错误 | 知识内容、结构、分块或嵌入表示在转换中失真，破坏源内容与知识对象的对应关系。 | 81 | 30 | 37.04% |
| 逻辑与校验错误 | 分块、过滤、召回、重排或引用对应规则未按指定策略生效。 | 62 | 11 | 17.74% |
| 接口契约错误 | 文档结构、编码输入、父分块、来源信息或检索文本在组件交互中不符合约定。 | 52 | 11 | 21.15% |
| 状态一致性错误 | 文档、分块、图片、图实体与索引的关联或更新状态不同步，或检索对象与请求范围不一致。 | 46 | 13 | 28.26% |
| 依赖与环境错误 | 嵌入输入容量、图索引读写路径或知识抽取配置与框架使用约定不一致。 | 39 | 5 | 12.82% |
| 资源管理不当 | 页面加载、分块编码或候选重排的容量和生命周期处理破坏知识内容完整性或候选输入要求。 | 26 | 5 | 19.23% |
| 安全漏洞 | 当前样本涉及通用身份认证、授权与租户隔离，未识别到满足上述规则的RAG特有情形。 | 21 | 0 | 0.00% |
| 提示词与上下文错误 | 检索证据、来源信息或知识抽取提示在传递、组织和裁剪中出错。 | 6 | 2 | 33.33% |

当前333条样本中，RAG特有根因为77条，占23.12%；通用根因为256条，占76.88%。上表各行比例以该一级类别的样本数为分母。逐例结果以`data/RAG根因二级标注.csv`为准，不由所在阶段或一级类别自动生成。

典型案例：[Kotaemon #456](https://github.com/Cinnamon/kotaemon/issues/456)将分块重叠量设为`0`，实现却通过`chunk_overlap or 256`将合法零值替换为默认值；[关联修复](https://github.com/Cinnamon/kotaemon/pull/457)改为判断参数是否为`None`。一级根因为逻辑与校验错误，二级判定为RAG特有根因，因为默认值判断直接破坏了用户指定的零重叠分块策略。

## 7. 修复策略

### 7.1 主表的修复操作标签

主表保留以下九个实际使用的标签。这些标签描述333条记录的主要修改操作。

| 标签 | 含义 |
| --- | --- |
| `add_validation_or_guard` | 增加或修正条件判断、输入校验、边界保护及缺失值处理。 |
| `fix_data_processing_or_indexing` | 修正解析、转换、编码、分块、索引或数据读写。 |
| `fix_retrieval_or_ranking` | 修正召回、过滤、候选选择、排序或重排。 |
| `fix_prompt_or_generation` | 修正模型输入组织、生成过程、流式返回或响应包装。 |
| `adapt_api_or_schema` | 对齐接口字段、类型、结构、协议或服务适配。 |
| `fix_state_or_workflow_logic` | 修正状态同步、持久化、会话隔离或工作流数据传递。 |
| `fix_resource_handling` | 修正资源释放、复用、容量、生命周期或并发控制。 |
| `update_dependency_or_config` | 修改依赖声明、版本约束、运行配置或部署设置。 |
| `fix_ui_or_api_behavior` | 修正界面、交互、页面跳转或通用API行为。 |

修复操作与根因不一一对应。例如，增加权限校验可以修复安全漏洞，字段对齐也可能恢复状态同步。测试、文档和伴随性重构不因与修复同时提交而成为主修复策略。

### 7.2 RQ4的小规模修复模式

论文对筛选后的122项小规模任务归纳了六类修复模式：显式区分缺失值与合法假值；对齐接口与数据模式契约；转换文档与检索数据的表示形式；隔离会话状态并兼容旧版状态；补充RAG特有的检索与上下文约束；管理文件资源与监视器事件的生命周期。

这六类模式是对小规模修复的进一步归纳，不等同于主表中九个操作标签的一一替换。当前结果表保留操作标签，六类模式的逐例独立编码记录未包含在本包中。

## 8. 标注与复核流程

1. **样本筛选**：检查Issue状态、缺陷标签、框架维护责任、PR合并记录及直接修复关系；识别重复报告和无关关联。
2. **试点标注**：按框架分层抽取30%的样本，共100条，阅读两侧证据，采用开放编码形成分类，讨论边界后冻结手册，并依据冻结规范复标试点样本。
3. **正式独立标注**：两名标注者对其余233条分别填写主症状、主根因和相关总结。功能阶段与修复操作依据相关实现及核心修复判定。
4. **一致性与分歧处理**：使用讨论和仲裁前的独立标签计算Cohen's Kappa。症状与根因分别计算，不能将一个维度的系数作为另一维度的结果；分歧由讨论或第三名研究者仲裁解决。
5. **二级判定**：在一级标注完成后，对333条样本按第6.3节独立判定RAG特有或通用情形，再处理分歧。
6. **证据复核**：检查症状、根因、核心修改及框架责任是否对应；区分代码逻辑推断与公开运行证据，核对所有总结字段与标签。
7. **冻结发布**：按Issue链接检查唯一性，核对标签集合、各框架数量、关联表覆盖范围及最终统计，再保存发布版本。

论文报告的症状、根因及RAG特有/通用判定的Kappa系数分别为0.87、0.91和0.85。公开表保存最终标签，不包含用于重新计算这些系数的双人原始独立评分矩阵；统计脚本不从最终标签反推Kappa。

证据不足时先在工作记录中保留问题、缺少的证据与待复核状态，经补充证据和讨论后再决定最终标签或排除。`unknown`不是当前发布数据的症状、根因或阶段类别，不用于替代未完成的判定。

## 9. 分析数据与度量口径

| 文件 | 用途 |
| --- | --- |
| `BUG汇总.xlsx` | 333条Issue–PR的一级标注与采集字段。 |
| `data/RAG根因二级标注.csv` | 333条样本的RAG特有/通用最终分类。`rag_specific=1`为RAG特有，`0`为通用。 |
| `data/RQ3_样本与指标.csv` | 全部333条的指标及筛选记录；`rq3_included=1`的317条用于RQ3。 |
| `data/RQ5_候选代码与语义审查.csv` | 122项任务的保存结果与最终人工评价。 |

RQ3指标按以下口径计算：

- `open_duration_days`：Issue关闭时间减创建时间，以秒数除以86,400得到连续天数，不使用主表中的整数天数代替。
- `issue_comments`：Issue评论数量；`pr_comments`：采集接口返回的PR普通评论数量，不另加行内审查评论或Review记录；`discussion_count`：二者之和。此合计口径对应已有分析脚本，不能称为单独的Issue评论数。
- `changed_lines`：选定PR保存的新增与删除行数之和，不等于人工识别的最小修复行数，也未统一剔除测试、文档、空白或格式调整。
- `rq3_exclusion_reason`：16条混合或非针对性提交记录的RQ3排除依据。该列不改变主表的一级标签。

评论数量和PR元数据是采集时的快照，可能与当前网页不同。原始元数据字段与人工判定应分别保留。

框架等权比例为四个框架内部类别比例的算术平均，全样本比例为类别总数除以333。二者分别描述不同汇总权重下的结果，不能相互替代。

## 10. RQ5人工语义审查

RQ5使用122项局部化修复任务。实验提供Issue信息、缺陷相关路径及修复前局部代码，不提供真实修复PR或开发者补丁；模型不联网、不调用工具、不检索仓库，`temperature=0`、`top_p=1`，每项任务每个模型生成一次候选代码。调用参数由实际请求配置控制，不能仅靠提示词保证。

`标注工具/RQ5提示词.txt`保留仓库中的实验模板原文。为避免改变已完成实验的条件，本次手册更新不修改该模板。

人工评价检查候选代码是否针对目标异常、满足已知实现与接口约束，并保留无关行为。两名评价者在盲化条件下独立评价，分歧交由第三名评价者处理。论文报告评价一致性Kappa为0.82。

结果表中`deepseek_semantic_accepted`和`gpt_semantic_accepted`的`1`表示人工语义审查通过，`0`表示未通过；它们分别对应原实验文件的`is_fixed`与`is_fixed.1`，评价值未改变。DeepSeek-V4-Flash为54/122，GPT-5.4-mini为51/122。

`deepseek_candidate_code`与`gpt_candidate_code`分别保存两模型的原始候选输出。结果表中的根因标签、根因总结与`how_to_fix_bug`属于标注和评价材料，不应一并作为修复生成输入。

语义审查通过率反映候选代码的人工评价结果。模型生成代码未经过完整项目构建、缺陷触发与回归验证，不能将该指标解释为运行测试通过率。结果表保存了模型输出与最终评价，但未逐任务保存可直接重放的完整API请求和全部局部输入，因此本包主要支持结果核查与评价复核。
