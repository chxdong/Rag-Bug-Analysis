# RAG 框架 BUG 数据标注 Codebook

> 适用框架：RAGFlow、FastGPT、Kotaemon、AnythingLLM  
> 标注单位：一条 BUG Issue 及其关联的 selected merged PR  
> 当前日期：2026-06-11  
> 使用原则：本文件只列出当前有效标签和正式标注流程。

## 1. 标注目标

本研究从 Issue 中识别 BUG 的外在表现，从关联并已合并的 PR 中判断缺陷所在阶段、技术根因和修复方式。每条样本只标注一个主要阶段、一个主要症状、一个主要根因和一个主要修复策略。

标注时必须区分以下维度：

- `bug_stage`：BUG 主要发生在 RAG 流程或工程系统的哪个阶段。
- `bug_run_symptom_type`：用户或开发者直接观察到什么异常表现。
- `bug_root_cause_type`：代码层面为什么出现该 BUG。
- `fix_strategy`：开发者通过什么主要方式修复该 BUG。

症状和根因是正交维度。不能根据症状直接推断根因，也不能根据修改文件所在模块直接推断症状。

## 2. 标注字段

| 字段 | 标注要求 |
| --- | --- |
| `功能阶段` | 选择 BUG 主要发生的阶段 |
| `缺陷问题总结` | 用中文概括整个 BUG 的问题，包括触发场景和异常行为 |
| `运行症状总结` | 用中文说明 BUG 在运行时造成的直接可观察影响 |
| `缺陷症状` | 从当前症状标签中选择一个 |
| `缺陷根因总结` | 用自然、具体的中文概括造成 BUG 的技术原因 |
| `缺陷根因` | 从当前根因标签中选择一个 |
| `缺陷修复步骤` | 用中文概括修复操作 |
| `缺陷修复策略` | 从当前修复策略中选择一个 |

## 3. BUG 阶段标签

本研究的 `bug_stage` 并非凭经验任意划分，而是综合借鉴三类相近研究后做出的适配性设计：

1. **RAG 应用与 LLM-enabled software 工作流研究**  
   `2407.05138v1.pdf` 将 RAG 工作流概括为两个核心阶段：  
   - **storage phase**：文本提取、切分、embedding、向量存储；  
   - **query stage**：问题向量化、知识召回、上下文构造与生成。  
   这一划分为本文提供了最核心的 RAG 主链路依据。

2. **LLM Agent / RAG 框架缺陷研究**  
   `A_Characterization_Study_of_Bugs_in_LLM_Agent_Workflow_Orchestration_Frameworks.pdf` 将框架结构抽象为 `data preprocessing`、`core schema`、`agent construction`、`featured modules` 等组件，说明面向框架的缺陷研究不能只看算法链路，还必须覆盖编排、模块组织和特色能力层。

3. **向量数据库缺陷研究**  
   `Toward Understanding Bugs in Vector Database.pdf` 将系统划分为 `query`、`index`、`storage` 等层，表明检索系统中的问题通常应区分为“数据如何存进去”“查询如何取出来”“底层存储和索引如何维护”几个不同位置。

基于上述文献，本文采用一种**“RAG 主链路 + 框架支撑层”**的阶段分类方式。也就是说：

- 对 RAG 核心链路，保留 `knowledge_preparation`、`retrieval_reranking`、`response_generation` 三个主阶段；
- 对框架工程特征，再补充 `knowledge_base_management`、`model_provider_integration`、`workflow_agent_orchestration`、`ui_api_deployment` 四个支撑阶段。

这种做法比单纯照搬“storage/query”两段式更细，因为我们的研究对象不是单个 RAG 应用，而是具备知识库、工作流、外部 provider 和部署界面的**开源框架**；但它又比完全开放编码更稳，因为每个阶段都能回溯到已有研究中的结构概念。

| 标签 | 定义与判定范围 |
| --- | --- |
| `knowledge_preparation` | 文档或原始内容被转换为“可存储、可索引、可检索”知识单元的准备阶段。包括文件上传、URL/第三方数据导入、内容读取、文档解析、OCR、版面还原、文本清洗、字段抽取、chunk 切分、embedding 生成、索引构建、索引写入和训练/预处理任务。凡是问题核心出现在“知识还没进入稳定可检索状态之前”的样本，优先标该阶段。 |
| `retrieval_reranking` | 已经存在知识单元或索引后，系统为当前请求执行召回、过滤、Top-K 选择、混合检索、元数据过滤、候选结果组织和 rerank 的阶段。只要 BUG 的核心在“应该检到什么、按什么顺序给出什么候选结果”，而不是文档本身如何被解析或模型如何最终生成回答，优先标该阶段。 |
| `response_generation` | 检索结果或用户输入被组织为模型可消费上下文，并触发生成、流式输出和结果包装的阶段。包括上下文拼接、历史消息选择、Prompt 构造、引用装饰、token 裁剪、LLM 调用、流式返回、答案后处理、引用和证据关联等。凡是问题核心在“模型吃到什么输入、如何生成、如何把回答返回给用户”，优先标该阶段。 |
| `knowledge_base_management` | 知识库及其资源对象的管理阶段。包括 knowledge base、dataset、collection、workspace、folder、document record、metadata、标签、权限、归属关系、删除/恢复、同步状态和资源可见性管理。凡是 BUG 的核心不在内容处理本身，而在“知识对象怎么被组织、管理、授权和展示”，优先标该阶段。 |
| `model_provider_integration` | RAG 框架与外部模型能力或基础服务的接入适配阶段。包括 LLM、embedding、reranker、向量数据库、OCR 服务、第三方推理服务、SDK、认证方式、请求参数、返回字段和 provider 兼容层。凡是问题核心在“框架与外部 provider/服务如何对接”，优先标该阶段。 |
| `workflow_agent_orchestration` | 多步骤执行和流程编排阶段。包括 workflow、Agent、Tool、节点调度、状态传递、分支控制、循环、任务链、插件调用、计划执行和跨节点数据流。凡是 BUG 的核心在“多个步骤或节点如何衔接、执行和传递状态”，优先标该阶段。 |
| `ui_api_deployment` | 面向用户或开发者的通用交互与工程运行阶段。包括前端页面、表单、按钮、路由、普通 REST API、鉴权、会话入口、服务部署、Docker、环境变量、启动脚本、网关、反向代理和文档页面。凡是问题核心不在 RAG 主链路内部机制，而在系统交互面或工程运行面，优先标该阶段。 |
| `unknown` | 现有证据无法确定主要阶段 |

### 3.1 阶段体系设计原则

为保证阶段划分既有文献依据，又能适配当前四类 RAG 框架，本文在设计时遵循以下原则：

1. **优先对齐 RAG 信息流，而不是对齐目录结构。**  
   阶段首先反映知识和请求在系统中的流动路径，而不是简单按文件夹、模块名或前后端边界切分。

2. **先保留 RAG 核心三段，再补充框架支撑层。**  
   `knowledge_preparation`、`retrieval_reranking`、`response_generation` 是核心信息链；其余四类用于承接框架特有的资源管理、编排、接入和部署问题。

3. **阶段回答“错误主要形成在哪里”，而不是“最后在哪里被看到”。**  
   用户可能在页面上看到异常，但真正的错误可能早已形成于索引、检索或生成链路内部。

4. **阶段粒度必须服务于跨框架比较。**  
   如果分得过细，会导致不同框架之间无法对齐；如果分得过粗，又无法区分 RAG 核心链路和框架工程层的差异。

5. **阶段与根因保持正交。**  
   例如同样是 `retrieval_reranking`，既可能由 `logic_validation_error` 引起，也可能由 `api_contract_error` 或 `state_consistency_error` 引起。

### 3.2 阶段判定规则

1. 以 BUG 首次产生错误的主要位置为准，而不是用户最后看到错误的位置。
2. 跨越多个阶段时，优先选择 selected PR 核心修复所在阶段。
3. provider 的请求参数、响应字段或认证适配问题标 `model_provider_integration`。
4. 通用前端、API、部署或鉴权问题标 `ui_api_deployment`。
5. 无法稳定确定主要阶段时标 `unknown`，不要凭 Issue 标题猜测。

### 3.3 关键阶段边界

#### `knowledge_preparation` 与 `retrieval_reranking`

- 文档解析失败、OCR 错误、Chunking 异常、embedding 生成错误、索引构建/写入错误，标 `knowledge_preparation`。
- 文档已经成功入库，但召回范围、过滤条件、Top-K、Rerank 顺序或候选组织错误，标 `retrieval_reranking`。
- 简单地说：前者关注“知识怎么被做出来”，后者关注“知识怎么被找出来”。

#### `retrieval_reranking` 与 `response_generation`

- 检索阶段问题关注“应该给模型哪些候选片段”，标 `retrieval_reranking`。
- 生成阶段问题关注“这些候选片段如何被拼进 Prompt/上下文，以及模型如何输出结果”，标 `response_generation`。
- 即使最终表现为回答错误，只要修复核心在检索过滤、排序或召回规则，仍标 `retrieval_reranking`；若修复核心在 Prompt、history、context 拼接或 token 裁剪，则标 `response_generation`。

#### `knowledge_preparation` 与 `knowledge_base_management`

- 内容处理、切分、embedding、索引训练、预处理任务本身出错，标 `knowledge_preparation`。
- 知识库对象的创建、删除、归属、权限、可见性、同步标记或资源管理出错，标 `knowledge_base_management`。
- 文档“处理过程错了”属于前者；文档“作为一个知识对象被管理错了”属于后者。

#### `model_provider_integration` 与 `response_generation`

- 如果问题核心在请求参数、认证方式、返回字段、SDK 兼容或 provider 适配层，标 `model_provider_integration`。
- 如果 provider 能正常被调用，但传给模型的 Prompt、context 或 history 组织错误，标 `response_generation`。
- 简单说：接不上外部服务是 `model_provider_integration`，接上了但喂给模型的输入不对是 `response_generation`。

#### `workflow_agent_orchestration` 与其他阶段

- 若 BUG 核心在多个节点、多个 Tool、多个步骤之间的调度、状态流转和执行顺序，标 `workflow_agent_orchestration`。
- 若某个节点内部本身是文档解析、检索或生成错误，而工作流只是承载位置，则优先标该节点实际出错的功能阶段，而不是一律标工作流。
- 只有当修复核心确实落在编排层、节点连接关系或跨步骤状态传播时，才标 `workflow_agent_orchestration`。

#### `ui_api_deployment` 与功能阶段

- 页面显示、按钮行为、路由跳转、普通 API 响应、鉴权、部署、环境配置和服务启动问题，标 `ui_api_deployment`。
- 如果 UI/API 只是暴露症状，而修复核心在文档处理、检索、生成、provider 接入或工作流内部机制，则标实际出错的功能阶段。
- 不要因为用户最先在页面上看到异常，就把所有问题都标成 `ui_api_deployment`。

## 4. 症状标签

症状只描述外在异常表现，不描述造成异常的技术原因。

| 标签 | 定义 | 典型示例 |
| --- | --- | --- |
| `crash` | 当前操作在正常运行过程中被明确异常中断，通常表现为接口 500、未捕获异常、任务失败、解析报错或请求直接终止 | 接口返回 500；上传或解析文档时报错；模型调用异常后当前请求直接失败 |
| `performance_cost_issue` | 系统不一定立刻报错，但出现明显卡顿、挂起、超时、冻结、重复下载、重复输出、资源异常消耗或长链路越来越慢 | Agent 长时间转圈后超时；前端持续卡顿冻结；模型文件反复下载；流式输出重复 |
| `build_failure` | 缺陷发生在安装、构建、镜像、依赖、迁移、容器启动或服务启动阶段，系统还未进入正常服务状态就失败 | Docker build 失败；Nginx 启动失败；依赖冲突导致服务无法启动 |
| `functional_failure` | 功能入口仍可进入或部分执行，但结果、状态或行为不符合预期，且不会先以明确异常终止。它是宽口径症状，覆盖数据状态错误、响应结果异常、UI/API 行为异常、provider 接入异常、知识库操作异常、workflow/agent 异常及配置不生效等 | 滚动到底失败；文档显示已嵌入但无法检索；引用 URL 错误；页面元素消失；默认行为与兼容接口不一致 |
| `unknown` | Issue 与 PR 证据不足，无法稳定判断用户可见症状 | Issue 描述过短，PR 也未说明修复效果 |

### 4.1 症状判定顺序

依次检查以下问题，命中后停止：

1. 是否发生安装、构建、容器创建或服务启动失败？是则标 `build_failure`。
2. 是否在正常运行期间明确抛异常、返回 500 或任务失败终止？是则标 `crash`。
3. 是否未明确失败，但出现挂起、超时、显著变慢、资源或 token/cost 异常？是则标 `performance_cost_issue`。
4. 是否为其他功能行为偏离预期？是则标 `functional_failure`。
5. 证据不足则标 `unknown`。

### 4.2 关键症状边界

- `functional_failure` 是当前数据中占比最高的症状类别，但它不是“兜底桶”。它专门表示系统没有先崩溃，而是向用户暴露了错误结果、错误状态或错误行为。论文中可结合 `bug_stage` 再拆分为 UI/API 行为异常、provider 接入异常、知识库操作异常、workflow/agent 异常、数据状态错误和响应结果异常等二级子类型。
- 检索、解析、嵌入、索引或生成出错不是独立症状标签。应根据用户实际看到的是异常终止、性能拖慢还是错误结果，在 `crash`、`performance_cost_issue`、`functional_failure` 中选择，具体位置由 `bug_stage` 表达。
- 页面显示、按钮、导航、普通 API 行为和配置操作异常通常标 `functional_failure`。
- 越权、隐私泄露和跨租户访问的外在表现通常标 `functional_failure`，技术根因标 `security_vulnerability`。
- 请求长期不返回、越来越慢、持续冻结、重复下载或重复输出标 `performance_cost_issue`；请求明确返回 500 或抛异常终止标 `crash`。
- 启动阶段失败标 `build_failure`；启动成功后某个请求失败不标 `build_failure`。
- 数据丢失、未保存、残留、更新不生效、假成功、引用错误或返回结果不符合预期等，若没有先以异常终止暴露，统一标 `functional_failure`。

## 5. 根因标签

根因必须优先依据 selected merged PR 的修改文件、diff、标题、描述和评论判断。

| 标签 | 定义与详细判定范围 |
| --- | --- |
| `logic_validation_error` | 普通控制逻辑、条件分支、默认值处理、边界校验、只读字段拦截、滚动状态判断、布局判断等实现错误。也包含检索、召回、Top-K、过滤、Rerank、混合检索权重等策略逻辑或参数配置不当，只在问题不能更准确归入其他机制时使用 |
| `data_processing_error` | 数据在解析、转换、编码、切分、Chunking 分块、序列化、反序列化、字段拼装、内容抽取或单次写入过程中被错误处理，强调“数据这一步本身已经被处理错了” |
| `prompt_context_error` | 模型或 Agent 调用前，语义输入载荷在选择、组织、格式化或裁剪过程中发生错误。包括 Prompt 模板与配置、system/user/assistant/tool 消息组织、历史消息的线程筛选与窗口截取、检索证据及其元数据向模型上下文的装配、多模态附件或工具结果注入，以及 token 预算与上下文裁剪。只有 PR 的核心修改直接改变模型实际接收的输入内容或消息结构时使用该类 |
| `state_consistency_error` | 一次操作后，不同组件、请求、时间点或存储副本看到的状态不一致，或者失败结果被错误上报为成功。强调“状态没有同步到该同步的地方” |
| `api_contract_error` | 外部 provider API、内部 API、字段、参数、schema、默认值、兼容行为或协议契约不匹配，强调调用双方对接口约定的理解不一致 |
| `resource_mismanagement` | 资源生命周期或并发控制处理不当，包括超时、清理函数、进程隔离、重复下载、重复渲染、连接、线程、队列和高成本状态更新等问题 |
| `dependency_environment_error` | 依赖库、Docker/镜像、运行环境、部署配置、权限、路径、环境变量、外部工具或样式作用域环境不兼容或设置错误 |
| `security_vulnerability` | 权限、身份、租户隔离、资源所有权、只读边界或敏感操作保护缺失，导致越权访问、跨租户读写、权限绕过、密码处理错误或未授权操作 |
| `unknown` | Issue、PR 描述、修改文件和 diff 均不足以支持稳定判断 |

### 5.1 单主根因判定顺序

当一个样本看似符合多个根因时，按 selected merged PR 的核心修复内容判断：

1. 越权、身份、租户隔离、访问控制、注入或数据泄露：`security_vulnerability`。
2. 资源释放、并发、竞态、重复初始化或队列阻塞：`resource_mismanagement`。
3. API 字段、参数、schema、协议或 provider 返回结构不匹配：`api_contract_error`。
4. 依赖版本、环境、Docker、路径、默认配置或环境变量：`dependency_environment_error`。
5. 跨组件、跨请求、跨时间或跨副本状态不同步：`state_consistency_error`。
6. 模型调用前的 Prompt、消息历史、检索证据、工具结果、多模态附件或 token 裁剪组织错误：`prompt_context_error`。
7. 数据解析、转换、编码、Chunking、序列化或单次持久化错误：`data_processing_error`。
8. 其余条件、流程、算法、检索策略或普通校验问题：`logic_validation_error`。
9. 证据不足：`unknown`。

### 5.2 关键根因边界

#### `logic_validation_error` 与 `data_processing_error`

- 条件、算法、默认值、流程、滚动状态、布局规则、普通边界检查，以及检索、召回、Top-K、过滤、Rerank、混合检索权重等策略逻辑或参数错误标 `logic_validation_error`。
- 编码、解析、序列化、类型转换、字段拼装、内容抽取、Chunking 分块或单次读写错误标 `data_processing_error`。
- 如果“数据处理这一步本身错了”，标 `data_processing_error`；如果处理函数本身没问题，而是外围判断或分支没兜住，标 `logic_validation_error`。

#### `prompt_context_error` 与 `logic_validation_error`

- PR 主要修改传递给模型的 Prompt 模板或配置、角色消息、历史线程筛选、上下文窗口、检索证据装配、工具结果、多模态附件注入或 token 裁剪，标 `prompt_context_error`。
- PR 主要修改普通 if/else、循环、参数顺序或非 LLM 输入相关校验，标 `logic_validation_error`。
- 检索、召回、Top-K、过滤、Rerank 或混合检索权重本身的策略问题不标 `prompt_context_error`，即使它们最终影响了模型回答。
- 外部 provider 的字段或 Schema 不匹配标 `api_contract_error`；通用解析、编码或序列化错误标 `data_processing_error`；缓存、数据库或前端状态不同步标 `state_consistency_error`。只有这些处理直接服务于模型输入载荷的构造，且 PR 核心修改模型实际接收的消息内容或结构时，才标 `prompt_context_error`。
- 模型回答错误，或 Issue/PR 中仅出现 prompt、context、LLM 等词，均不能单独证明该根因。

#### `state_consistency_error` 与 `data_processing_error`

- 单次解析、转换、Chunking、序列化、写入或读取操作本身错误，标 `data_processing_error`。
- 单次操作可能已经执行，但缓存、数据库、索引、前端、线程或会话之间状态不同步，标 `state_consistency_error`。
- “文档本身没嵌入成功却被标成成功”“页面状态没刷新但后台已更新”都优先标 `state_consistency_error`。

#### `api_contract_error` 与 `dependency_environment_error`

- 调用参数、字段、schema、默认值、认证方式、兼容行为或响应结构不匹配，标 `api_contract_error`。
- 依赖版本、环境变量、Docker、部署权限、启动脚本、外部工具或运行环境错误，标 `dependency_environment_error`。
- 通过适配字段、参数或兼容行为修复，通常标 `api_contract_error`；通过改镜像、依赖、权限、路径或环境配置修复，通常标 `dependency_environment_error`。

#### `state_consistency_error` 与 `resource_mismanagement`

- 正确状态没有在组件、请求或存储副本之间同步，标 `state_consistency_error`。
- 如果修复核心是超时控制、清理函数、进程隔离、重复下载、重复渲染、并发写入或资源生命周期管理，标 `resource_mismanagement`。

#### `security_vulnerability` 与普通校验错误

- 普通空值、范围或格式校验缺失标 `logic_validation_error`。
- 校验缺失直接导致身份伪造、越权访问、跨租户操作或数据泄露时，标 `security_vulnerability`。

## 6. 修复策略标签

| 标签 | 定义 |
| --- | --- |
| `add_validation_or_guard` | 增加输入校验、空值检查、异常保护或权限检查 |
| `fix_data_processing_or_indexing` | 修改文档解析、格式转换、chunking、embedding、索引或知识条目处理 |
| `fix_retrieval_or_ranking` | 修改检索、过滤、排序、rerank 或 top-k |
| `fix_prompt_or_generation` | 修改 Prompt、上下文拼接、消息历史、token 裁剪或生成输入输出组织 |
| `adapt_api_or_schema` | 适配 provider、SDK、API schema、字段、协议或认证方式 |
| `fix_state_or_workflow_logic` | 修改状态同步、持久化、版本一致性、workspace、session、workflow 或 Agent/Tool 逻辑 |
| `fix_resource_handling` | 修改资源释放、资源复用、并发控制、重复初始化或队列处理 |
| `update_dependency_or_config` | 升级或锁定依赖，修改 Docker、配置或环境变量 |
| `fix_ui_or_api_behavior` | 修改前端显示、页面跳转、按钮、组件交互或通用 API 行为 |
| `add_or_update_tests` | 主要修改测试或补充回归测试 |
| `refactor_without_behavior_change` | 以重构为主，行为变化不明显 |
| `unknown` | 无法稳定判断主要修复方式 |

修复策略描述 PR 做了什么，与根因不要求一一对应。例如，`security_vulnerability` 可以通过 `add_validation_or_guard` 修复。

## 7. 正式标注流程

### 步骤 1：确认样本有效性

1. 确认 Issue 是框架本身的运行时或工程缺陷，而不是纯咨询、功能请求或仅文档问题。
2. 确认关联 PR 已 merged。
3. 多个已合并 PR 时，保留与 Issue 修复最直接的 PR；无法区分时选择最新 merged PR，并在 `notes` 说明。

### 步骤 2：阅读 Issue 并判断症状

1. 阅读 Issue 标题、正文、复现步骤、日志、截图和评论。
2. 用中文完成 `bug_issue_summary`，概括触发场景、异常行为和主要影响。
3. 用中文完成 `bug_run_symptom_summary`，只描述运行时可观察结果。
4. 按症状判定顺序选择唯一的 `bug_run_symptom_type`。

### 步骤 3：阅读 PR 并判断阶段和根因

1. 阅读 PR 标题、正文、评论、提交信息和修改文件列表。
2. 查看 PR diff；diff 过长时，优先查看修改文件、关键函数、测试和 Issue/PR 评论。
3. 识别 BUG 首次产生错误的主要位置，选择唯一的 `bug_stage`。
4. 用自然中文完成 `bug_root_cause_summary`，说明具体错误机制，不写“根据 PR”“相关执行路径”等机械表述。
5. 按单主根因判定顺序选择唯一的 `bug_root_cause_type`。

### 步骤 4：判断修复方式

1. 用中文完成 `how_to_fix_bug`，直接说明如何修复，不写“PR 修改了某文件”。
2. 根据核心修复操作选择唯一的 `fix_strategy`。

### 步骤 5：记录证据与备注

1. 记录 2 至 4 条关键证据，包括 Issue 现象、PR 说明、修改文件或关键 diff。
2. 对多标签边界、证据不足、PR 修改范围过大或 Issue-PR 关联较弱的情况填写 `notes`。

### 步骤 6：交叉复核

1. 复核症状是否只描述外在表现，根因是否有 PR 证据支持。
2. 复核 `bug_issue_summary`、`bug_run_symptom_summary`、`bug_root_cause_summary` 和 `how_to_fix_bug` 是否描述了 BUG 本身，而不是解释字段含义。
3. 复核四个标签均来自当前标签集合，没有自由造词。
4. 对 `unknown` 和边界争议样本进行第二标注者复核。
5. 定期抽样复核高频标签，避免将 `functional_failure` 或 `logic_validation_error` 当作默认类别。
