# RAG框架缺陷特征与修复策略的实证研究

本仓库提供论文《RAG框架缺陷特征与修复策略的实证研究》（*An Empirical Study of Defect Characteristics and Repair Strategies in RAG Frameworks*）的相关数据、人工标注结果、分析材料、大语言模型生成结果及复现实验说明。

## 研究概述

检索增强生成（Retrieval-Augmented Generation，RAG）框架连接外部知识源与大语言模型，为知识检索、上下文构建和内容生成提供基础支撑。为系统认识端到端开源RAG框架中的真实代码缺陷及其修复过程，本研究选取以下四个具有公开Issue和Pull Request（PR）记录的开源框架：

- RAGFlow
- AnythingLLM
- FastGPT
- Kotaemon

研究共收集333组绑定缺陷标签且关联合并PR的Issue–PR样本，并从缺陷症状、功能阶段、技术根因、公开可观察修复投入和常见小规模修复策略等维度开展人工标注与定量分析。在此基础上，本研究进一步构建122项局部修复任务，用于探索大语言模型辅助生成候选补丁的能力。

## 研究问题

本研究主要回答以下问题：

1. RAG框架缺陷表现出哪些运行症状，并主要分布在哪些功能阶段？
2. RAG框架缺陷由哪些技术根因导致，根因与症状之间具有怎样的关系？
3. RAG框架缺陷的公开可观察修复投入呈现哪些特征？
4. RAG框架的小规模补丁中存在哪些重复出现的局部修复策略？
5. 大语言模型在局部化输入条件下生成RAG框架候选补丁的表现如何？

## 数据筛选与样本构成

| 分析内容                         | 样本数 | 说明                                                         |
| -------------------------------- | -----: | ------------------------------------------------------------ |
| 缺陷症状、功能阶段与技术根因分析 |    333 | 基础Issue–PR样本                                             |
| 修复投入分析                     |    317 | 排除版本发布、功能集合、代码重构及多问题混合提交等无法准确归因的记录 |
| 局部修复策略与大语言模型评测     |    122 | 对132组候选样本进一步筛选后形成的局部修复任务                |

这里的代码变更行数（Lines of Code，LOC）指关联PR中的代码增加行数与删除行数之和。Issue关闭时长、讨论量和PR变更行数仅作为公开可观察的修复投入代理指标，不等同于开发者的实际人时、认知成本或精确修复工作量。

## 标注与分析内容

### 缺陷特征

每组样本的分析证据主要包括Issue标题与正文、复现步骤、错误日志、截图、评论，以及关联PR的标题、说明、评论、修改文件、代码差异和测试变更。核心标注内容包括：

- 缺陷运行症状；
- 缺陷所在功能阶段；
- 缺陷技术根因；
- 修复方式与局部修复策略；
- Issue关闭时长、讨论量和关联PR变更行数。

### 小规模修复策略

筛选后的122项局部修复任务呈现出六类重复修复模式：

1. 显式区分缺失值与合法假值；
2. 对齐接口与数据模式契约；
3. 转换文档与检索数据的表示形式；
4. 隔离会话状态并兼容旧版状态；
5. 补充RAG特有的检索与上下文约束；
6. 管理文件资源与监视器事件的生命周期。

### 大语言模型评测

大语言模型评测使用122项局部修复任务。每项任务向模型提供Issue信息、缺陷相关文件路径及修复前的局部代码上下文，不提供真实PR、代码差异或开发者补丁。实验中禁止联网、搜索仓库和调用外部工具；设置 `temperature=0`、`top_p=1`，采用pass@1，每个模型对每项任务仅生成一次候选补丁。

候选补丁由两名评价者在盲化条件下独立进行人工语义审查，分歧由第三名评价者仲裁，评价者一致性Cohen’s κ为0.82。该评价主要判断候选补丁是否与Issue描述、代码上下文和目标修复语义一致，不等同于在完整仓库中经过构建、测试和回归验证的端到端修复。

## 主要结果

| 研究发现               | 结果                                                         |
| ---------------------- | ------------------------------------------------------------ |
| 主要运行症状           | 功能失效和运行崩溃共312条，占93.7%                           |
| 主要功能阶段           | 知识准备、系统交互与运行支撑共197条，占59.2%                 |
| 主要技术根因           | 数据处理、逻辑与校验、接口契约、状态一致性错误共241条，占72.4% |
| 修复投入代理指标中位数 | Issue关闭时长3.08天、讨论量3条评论、PR变更规模23 LOC         |
| 小规模补丁             | 132组样本不超过15 LOC，占39.6%                               |
| DeepSeek-V4-Flash      | 54/122个候选补丁通过人工语义评价，通过率44.3%                |
| GPT-5.4-mini           | 51/122个候选补丁通过人工语义评价，通过率41.8%                |

上述模型结果仅反映特定局部化输入、生成参数和人工语义评价标准下的候选补丁表现，不应解释为完整修复率、自动修复成功率或生产可部署率，也不用于对两个模型的综合能力进行排名。

## 复核与复现建议

1. 根据样本编号，将基础Issue–PR记录与人工标注结果对应。
2. 使用标注手册复核功能阶段、运行症状、技术根因和修复策略的定义。
3. 根据各研究问题的筛选规则分别载入333条、317条或122条样本。
4. 运行统计分析与绘图脚本，复核论文中的数量、比例、中位数和分布结果。
5. 使用仓库提供的提示词与实验参数重新生成候选补丁，并将输出与人工评价记录对应。

由于模型服务可能更新，即使使用相同模型名称和参数，重新生成的候选补丁也可能与本仓库保存的结果不同。为保证结果可核查，建议优先使用仓库中归档的原始模型输出和评价记录。

## 数据使用与有效性边界

- 本研究结论适用于所分析的四个具有公开Issue–PR记录的端到端开源RAG框架，不能直接推广至全部RAG框架、闭源平台、轻量级库或单一RAG组件。
- 数据来源于公开GitHub Issue和PR记录。引用、再分发上游代码或补丁时，应遵守对应开源项目的许可证及GitHub相关规则。
- Issue创建时间只能作为知识截止时间敏感性分析的分组依据，不能证明训练数据不存在重叠。
- 人工标注和语义评价可能受到研究者判断影响，仓库提供标注规则与复核材料，以支持独立检查。
